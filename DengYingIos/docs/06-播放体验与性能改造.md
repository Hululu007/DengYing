## 1. 用户提出的五项诉求（原文与拆解）

| # | 用户原话 | 拆解为可判定的需求 |
|---|---|---|
| 1 | 「首页每次进入加载很慢，加载完了之后要保存缓存，但不要过多保存，每一页都要」 | 首页分页结果**按页缓存**，有容量上限；二次进入同分类**不重新请求** |
| 2 | 「播放的时候加载缓存视频很慢…原先我逆向的两个软件播放都很快，只有偶尔会慢」 | **起播提速**：去掉起播前的阻塞探测；媒体数据落盘缓存，二次播放秒开 |
| 3 | 「进入详情页在内容上方放一个占位，点击剧集时视频在占位处播放；此时点击视频只出现进度条、暂停键和全屏键（手机与平板布局一致）」 | 详情页**内嵌播放器**；内嵌态控制栏为**精简三件套**；该形态**不区分设备类型** |
| 4 | 「全屏之后下方状态栏占画幅过多，应把上下集、倍速、退出全屏放一条线上；支持滑动屏幕跳转进度」 | 全屏控制栏**单行**；**横向滑动 seek** |
| 5 | 「暂停键和全屏键过小不美观」 | 控制键**尺寸达标且视觉协调**（≥44dp 热区，图标视觉 ≥24dp） |

## 2. 现状事实（侦察结论，作为设计输入）

### 2.1 首页慢的成因（代码事实）

| 位置 | 现状 | 问题 |
|---|---|---|
| `SourceRepository.fetchByCategory` | 每次调用都 `resolveTypeIds` → 各源 `ac=list` 请求 | 分类表**有 30 分钟内存+磁盘缓存**，但**列表结果本身不缓存** |
| 同上 | `coroutineScope { launch { resolveTypeIds(sources, cat, 999) } }` | 该 `coroutineScope` **会等待子协程完成**，后台补齐实际是**阻塞**的，等于白跑一遍全部分类映射 |
| `IndexViewModel.loadData` | 切分类即重新请求，无结果缓存 | 回到已看过的分类要重新等一遍 |
| `SourceRepository.fetchFromMapped` | 每批 3 个并发，收满 30 条即停 | 阈值与并发已合理，不是瓶颈 |

**结论**：首页慢的主因是**无结果缓存** + **一次白跑的阻塞补齐**。

### 2.2 起播慢的成因（真机探针证据）

```
[before-probe] urlLen=35
[after-probe]  elapsed=3042 m3u8=true seg=false host=https://hd.kuktxu.com
[probe-suspect-but-try-play]
[startEngine]  urlLen=35
```

| 位置 | 现状 | 问题 |
|---|---|---|
| `PlayerViewModel.resolveUrl` | 起播前串行做 `probeReachability`（**实测 3042ms**） | 该探测结果**当前已不作为准入条件**（`probe-suspect-but-try-play`），即**白等 3 秒** |
| 同上 | `loadVariants` 又是一次网络请求 | 非主列表时白等 |
| `Media3Engine` | 无磁盘缓存 | 二次播放要重新下载 |
| `PlayerFactory` 缓冲参数 | `min 15s / max 30s` | 起播门槛偏高（默认 50s 是有理由的，但 15s 对弱网仍偏严） |

**结论**：起播慢的主因是**两次白等的串行网络请求** + **无媒体缓存**。

### 2.3 详情页与全屏控制栏现状

| 项 | 现状 |
|---|---|
| 详情页 | 只有剧集按钮，点击后 `nav.navigate(player)` **跳页**；无内嵌播放位 |
| 全屏控制栏 | **两行**：进度行 + 控制行（倍速/上集/播放/下集/全屏）+ 连播行，底部占位高 |
| 手势 | 只有单击切换控制层显隐；**无滑动 seek** |
| 控制键 | `CtrlText` 固定 64×56dp，图标用文字字形（`⏸ ▶ ⏮ ⏭ ⤡ ⤢`），视觉偏小 |

## 3. 新增需求（FR-7xx）与验收条件

编号接续源工程体系（FR-4xx 播放、FR-5xx 个人资产之后新增 7xx 段表示「Android 移植特有」）。

| 编号 | 需求 | 验收条件 |
|---|---|---|
| **FR-701** | 首页分类结果按 `(源集合版本, 分类, 页码)` 缓存，容量有上限 | ① 二次进入同一分类第 1 页**不发网络请求**；② 缓存条目数 ≤ 上限；③ 超上限按 LRU 淘汰；④ 下拉刷新强制失效 |
| **FR-702** | 缓存持久化，冷启动仍有效 | ① 杀进程重启后同分类仍命中缓存；② 缓存有 TTL，过期后重新拉取 |
| **FR-703** | 起播前的可达性探测**不阻塞起播** | ① 点播放到 `setMedia` 之间**无网络等待**；② 探测转为后台进行，结果只用于"失败后换线" |
| **FR-704** | 媒体数据磁盘缓存，二次播放免重复下载 | ① 同一地址二次播放命中缓存；② 缓存总量有上限；③ 可在设置中清空 |
| **FR-705** | 详情页内容上方提供内嵌播放位，点击剧集**就地播放** | ① 点剧集后播放器出现在占位处，**不跳页**；② 占位有明确空态（未选剧集时）；③ 可一键转到全屏播放页 |
| **FR-706** | 内嵌态控制栏只含进度条、暂停键、全屏键 | ① 三个控件，无其他；② **手机与平板形态一致**（不做设备分支）；③ 点击画面切换显隐 |
| **FR-707** | 全屏控制栏为**单行** | ① 倍速、上一集、播放暂停、下一集、退出全屏在**同一行**；② 不遮挡画面（半透明浮层）；③ 系统栏不再额外占位 |
| **FR-708** | 支持横向滑动 seek | ① 在画面上横向滑动改变进度；② 滑动中显示目标时间与差值；③ 松手才真正 seek（不连续 seek）；④ 竖向滑动不触发 seek（竖向由亮度/音量占用，见 P-04/P-05） |
| **FR-709** | 控制键尺寸与视觉达标 | ① 热区 ≥44dp；② 主键（暂停/全屏）图标视觉 ≥24dp；③ 图标用矢量而非字体字形 |
| **FR-710** | **剧集可点性与播放条件绑定** | ① `displayEps` 非空即全部可点（不等资源站搜索）；② 点击后解析/换源期间显示状态文案；③ 无剧集数据时不可点 |
| **FR-711** | **全屏/返回 = 窗口形态切换，会话零中断** | ① 点全屏**不触发**任何解析/setMedia（探针无 `resolve-*`、无 `setMedia`）；② 全屏中会话继续播、进度连续；③ 返回详情页内嵌位**恢复同一会话继续播**；④ 全程无抖动、无瞬时暂停 |
| **FR-712** | seek 后未就绪保持缓冲指示 | ① 滑动/点击 seek 后若未 READY，缓冲圆环持续显示；② READY 后圆环消失 |
| **FR-713** | 播放会话**无瞬时播放后暂停** | ① 探针中 `play()` 后 2 秒内不得出现非用户发起的 `pause()`；② 播放中无"播一下就停"的观感 |

## 4. 设计

### 4.1 组件与职责（新增/改动）

| 组件 | 职责 | 目录 | 公开契约 | 依赖约束 |
|---|---|---|---|---|
| **`domain/page/PageCacheRules`** | 分页缓存的**纯策略**：键构造、TTL 判定、LRU 淘汰顺序 | `domain/` | `keyOf(...)` / `shouldServe(...)` / `evictOrder(...)` | 零 Android 依赖（可单测） |
| **`data/cache/PageCache`** | 分页结果的持久化与内存层 | `data/cache/` | `get/put/invalidate` | 依赖 `domain` + `Store` |
| **`data/cache/MediaCache`** | Media3 `SimpleCache` 的持有与生命周期 | `data/cache/` | `cacheDataSourceFactory(base)` | 依赖 `androidx.media3.datasource.cache` |
| **`playback/PlayerFactory`** | 数据源改为「缓存 + 网络」组合 | `playback/` | `mediaSource(url, headers)`（签名不变） | 依赖 `data/cache` |
| **`ui/pages/DetailScreen`** | 新增内嵌播放位与就地播放 | `ui/pages/` | 参数新增回调 | 依赖 playback |
| **`ui/components/InlinePlayer`** | 内嵌态播放器与精简控制栏 | `ui/components/` | Composable | — |
| **`ui/pages/PlayerScreen`** | 控制栏改单行；新增滑动 seek | `ui/pages/` | — | — |

### 4.2 依赖方向（保持既有约束）

```
ui ──> playback ──> domain
 │          ↑          ↑
 └──> data ─┴──────────┘     data ✗→ ui,  domain ✗→ 任何 Android 类型
```

新增的 `data/cache` 与 `domain/page/PageCacheRules` 遵守同一约束：
**缓存策略（TTL/淘汰）在 domain（可单测），IO 在 data。**

### 4.3 关键设计决策

#### D1：探测不再阻塞起播（FR-703）

**决策**：`resolveUrl` 直接 `startEngine`，探测改为**后台协程**；探测结果仅用于"播放器报错后是否值得换线"。

**理由**：探针实测该探测耗时 3042ms，而其结果**已不作为准入条件**（现行代码 `probe-suspect-but-try-play` 证明）。既然不阻塞决策，就不该阻塞用户。

**代价**：弱网下"探测本可提前发现死线路"的能力丧失，用户会多等一次播放器报错（约 1-2s）。
**权衡**：好源占多数（实测 tier1 三源均可播），多数用户体验提升 3s；坏源多花 1-2s 且随后换线。

#### D2：媒体缓存用 `SimpleCache`（FR-704）

**决策**：用 Media3 官方 `SimpleCache` + `CacheDataSource.Factory`，`LeastRecentlyUsedCacheEvictor`，上限 500MB。

**理由**：官方实现，无需自研；`SimpleCache` 的构造是**同步阻塞**的（源码 `conditionVariable.block()`），故必须在 IO 线程建、且**进程内单例**（源码：同一目录只允许一个实例）。

**风险**：SimpleCache 初始化在冷启动时可能耗时数百毫秒 → 处置：**懒初始化**（首次播放时才建），不阻塞首屏。

#### D3（**已修正**）：内嵌播放器与全屏播放页**共用同一个引擎**

> **修正记录（2026-10-17）**：初版决策是"内嵌态用独立引擎、不与全屏页共用"，
> 真机验证失败（点剧集长时间无画面、反复点击触发解码器抢占）。
> 查 [google/ExoPlayer Issue #9556](https://github.com/google/ExoPlayer/issues/9556)
> 后修正——官方维护者 claincly 明确说：
>
> > "The best approach would be keep one player instance and use it.
> > If you spin off multiple players, there will be time wasted in things like
> > codec init; and you might run out of available codec."
>
> 即：**全应用只保留一个 ExoPlayer 实例**，多个页面/位置只是它的不同"显示宿主"。
> 初版做法（每处各建一个引擎）正是官方反对的，代价是 codec 初始化浪费
> 与解码器耗尽——与真机现象一致。

**修正后的决策**：引擎由 `DengYingApp`（Application 作用域）持有，全局唯一。

**理由**：
- 官方推荐做法，避免 codec 初始化浪费与解码器耗尽
- 内嵌位与全屏页之间切换时**无需重建引擎**，转场更快、进度天然连续
- 不存在"两个引擎抢解码器"的问题

**代价**：需要处理"同一引擎被两处 UI 绑定"的时序（两处 `PlayerView` 不能同时绑同一 player）。
**处置**：用**引用计数**——`acquire()`/`release()` 配对，最后一处释放时才真正释放引擎。

#### D3.1：地址解析必须**提前**，不能等用户点击

真机探针显示：点击剧集后要串行跑「token 换链 → 分享页解析 → 跨源搜索」，
`[inline-alt-sources] n=5` 之后十几秒无输出，用户等不及返回触发
`JobCancellationException`。

**决策**：进入详情页时**立即在后台预解析首集地址**，用户点击时直接用已就绪的地址。

**理由**：用户在详情页浏览（看简介、挑剧集）通常有几秒，这段时间足够预解析。
点击时才开始的解析链必然让用户等——而"等待"就是"没反应"。

### D6（**架构修正**，2026-10-17 晚）：**单播放会话 + 视图宿主**，取代"页面间交接引擎"

> **修正记录**：D3 初版（两个页面各建引擎）和 D3 修正版（全局引擎 + 页面交接）
> 都在真机验证中失败。用户对目标行为的明确描述揭示了我对需求的根本误解：
>
> > "我点击全屏键是直接变成横屏，但不再一次触发视频加载……
> > 就相当于只是把视频窗口恢复到了那里而已。"
>
> 即：**全屏不是"另一个页面接管播放"，而是"同一个会话换了个窗口"**。
> 我此前的架构让详情页与播放页各自持 ViewModel、各自走解析链、
> 靠路由传参和生命周期回调交接引擎——这套交接产生了全部残留问题：
> 抖动、瞬时播放后暂停、退出全屏无声、返回不恢复。

**被否决的两版架构**：

| 版本 | 做法 | 失败证据 |
|---|---|---|
| D3 初版 | 内嵌位与全屏页**各建引擎** | 官方 Issue #9556 反对；解码器抢占 |
| D3 修正版 | 全局单例引擎 + **页面间交接**（路由传参 / 生命周期回调 / 引用计数） | 探针反复抓到：交接瞬间计数归零→pause；幂等跳过 setMedia 连 play 也跳过→全屏黑屏；`inlineState.isPlaying` 被转场暂停污染→恢复无声 |

**修正后的架构**：

```
PlaybackSession（Application 单例，播放会话的唯一所有者）
  ├── engine: Media3Engine（全局唯一）
  ├── sessionState: 会话状态（url/title/vodId/episode/position/status/errMsg）
  └── 操作: play(request) / pause() / resume() / seekTo()
        │
        ├── 详情页内嵌位 ──┐
        │                  ├── 都是同一会话的「视图宿主」，只读状态、转发操作
        └── 全屏播放页 ────┘
```

**三条铁律**：

1. **页面不拥有播放**。任何页面都不再调 `setMedia`/`resolveUrl`——
   播放的发起与迁移只发生在 `PlaybackSession`。
2. **全屏切换零播放操作**。点全屏 = `navigate(PLAYER)`，**仅此而已**；
   会话继续播，引擎不 pause、不交接、不重解析。返回同理。
3. **视图宿主只做两件事**：把引擎绑到自己的 `PlayerView`；把会话状态画出来。

**会话生命周期**：`play()` 发起时创建；详情页销毁且无全屏页时结束（pause 并保留进度）。

### D7：剧集可点性 = **具备可播地址**，与"资源站搜索完成"无关

> 用户原话："如果你能播放视频就是具备播放视频的条件，你就让剧集可以点击，
> 如果没有，则不可以点击，直到具备条件为止。"

**判定**：`displayEps.isNotEmpty()`（主线路 `vod_play_url` 给出了剧集地址）即**可点**。
预解析**只影响首集的起播速度**，不是可点的前提；换源兜底在点击后由会话执行并显示状态。

初版把可点性绑在「其他资源站搜索完成」上是错的——那是**换线候选**的加载，
与"这一集能不能播"无关。

### D8：seek 后未就绪 → **保持缓冲指示**

用户滑动跳转后若缓冲未完成，**继续显示缓冲圆环**（与起播同一口径），
不出现"松手后短暂黑屏/静帧无提示"的空窗。

### D9：禁止**瞬时播放后暂停**的抖动

任何路径都不允许出现"播一小段立刻暂停"。已知的两个来源在单会话架构下消除：
- 转场期间的 `surfaceInactive` 归零 pause（页面不再触发播放操作）
- 会话被多个 ViewModel 交错 pause/play

#### D4：滑动 seek 的方向判定（FR-708）

**决策**：用 `detectDragGestures` 并在手势越过阈值时**一次定模**——横向分量更大才进 seek，此后不再切换模式。

**理由**：`detectHorizontalDragGestures` 会在手势一开始就锁定横向，把"手指先竖后横"的常见操作丢掉；自己判主导方向既能容纳这种手势，又能让竖向分给亮度/音量。

**竖向归属（更新）**：竖向不再是"预留"，已由 P-04/P-05 占用——起点在左半屏调亮度、右半屏调音量，判定与实现见 `docs/08 §6.1`。一次手势只落入一种模式，从结构上排除"一次手势触发多个动作"。

**细节**：滑动中只更新"预览时间"，**松手才 seek**——连续 seek 会导致播放器频繁 seek 抖动。

#### D5：内嵌态控制栏手机/平板一致（FR-706）

**决策**：内嵌态**不做设备分支**，一律三件套。全屏态才区分（手机横屏单行、平板完整）。

**理由**：用户明确要求一致；且内嵌位尺寸由详情页版式决定，与设备类型无关。

### 4.4 缓存容量与淘汰（NFR-704）

| 缓存 | 上限 | 淘汰策略 | 位置 |
|---|---|---|---|
| 首页分页结果 | 30 页 | LRU（按最后访问时间） | `PageCacheRules`（纯函数） |
| 分类表 | 已有 30 分钟 TTL | 现有实现 | 不变 |
| 图片（海报） | 120 张（现有内存 LRU） | 现有实现 | 不变 |
| 媒体数据 | 500MB | `LeastRecentlyUsedCacheEvictor` | Media3 内置 |

**「不要过多保存」的落实**：三处容量都有硬上限，且**都有明确的淘汰规则**，不是"尽量多存"。

### 4.5 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| SimpleCache 目录被其他实例占用 | 播放崩溃 | 进程内单例；`SimpleCache.isCacheFolderLocked` 预检 |
| 缓存目录损坏 | 播放异常 | 初始化失败时**降级为无缓存**（不阻断播放） |
| 内嵌播放器与全屏切换时引擎泄漏 | 内存/解码器泄漏 | `onCleared` 释放；切换时先释放再新建 |
| 滑动 seek 与单击冲突 | 误触发 | 位移阈值（≥20dp）后才判定为滑动，否则仍算点击 |
| 单击因双击判定而延迟约 300ms | 控制层显隐手感变慢 | 这是区分单击/双击的固有代价，主流播放器一致；优先级定为"先判双击"（`docs/08 §2`） |
| 竖向手势与系统边缘返回冲突 | 误触亮度/音量 | 只在画面区域内生效；真机检查（`docs/08 §5`） |

**回滚**：每项改造独立提交，可单独 `git revert`。缓存类改动可通过常量（`PAGE_CACHE_LIMIT`、`MEDIA_CACHE_MB`）置 0 关闭。

### 7.1 下拉刷新 + 加载条

`IndexScreen` 接入 Material3 `PullToRefreshBox`，`isRefreshing` 由 **VM 的请求生命周期**
驱动（`UiState.refining`），不是"按钮被点了一下"——否则加载条会一跃而过。

刷新语义按 FR-701 第 ④ 条"下拉刷新强制失效"：先 `cache.invalidateAll()` +
`repo.clearClassCache()`，再拉第一页。

**刷新必须复位分页状态**（本轮修掉的真缺陷）：

| 字段 | 不复位会怎样 |
|---|---|
| `page` | 刷新拿到的是**第一页**，若沿用刷新前的页码（用户已翻到第 3 页），下次 `loadMore()` 会去拉第 4 页——第 2、3 页被永久跳过，且与当前列表不连续 |

而"该分类暂无内容"/"网络异常"正是用户最想下拉重试的时刻，故这两态改为
`fillMaxSize() + verticalScroll(rememberScrollState())`。

### 7.2 内嵌位返回残留（P-06 收口）

残留此前只挂 `ON_STOP → hidden = true`，而 `ON_STOP` 的时机由 Navigation 生命周期推进决定，
**不保证早于退出转场第一帧**。修法两条并用：

1. **导航层判据**：`NavHost` 传 `pageActive = (currentBackStackEntry.id == 本页 entry.id)`，
   内嵌位用 `hidden || !pageActive`。该判据在 `popBackStack()` 调用时立即成立，与转场时序无关。
2. **渲染面整块退出组合**（本轮补上）：`hidden` 此前只跳过**浮层**绘制，
   而 `AndroidView(PlayerView)` 仍留在组合里继续显示最后一帧——那正是"残留"。
   改为 `hidden` 时整个渲染面不进组合，`AndroidView` 被移除会同时把 `PlayerView` 从窗口摘下。
   会话不动（`ENGINE` 是全局单例），回详情页/回全屏重新挂载即可。

**遗留**：真机仍观察到返回转场首帧短暂见视频（约 1.2 秒后消失），见 `docs/05 §6`、`docs/08 §6.6` 待判断项。

## 8. B8：网络与聚合性能批次（2026-10-24）

起因：探针日志暴露三条慢路径，其中两条与"网络快不快"无关，是**并发编排写错了**。

### 8.1 关键结论：先证伪，再动手

初判是「`HttpClient.send` 的 `finally` 无条件 `conn.disconnect()` 掐掉了 keep-alive 池，
每个请求都重付 TCP/TLS 握手」。**实测证伪**：

- JDK 18：3 次连续 GET → 服务端只 `accept` **1** 次
- Android 16 真机（V2419A / SDK 36）：同样只 `accept` **1** 次

机制：`stream.use { }` 关闭流那一刻连接**已还回池中**；之后再 `disconnect()`
拿不回池里的连接，是空操作。JDK 文档说的 "may close the underlying socket if a
persistent connection is otherwise **idle** at that time" 指"流没读完、连接还挂在
当前请求名下"那种情况。

据此**回退**了 `drained` 判定逻辑（收益为零、只增复杂度），保留两处真有效的改动：

- `IO_BUFFER = 32 * 1024`（`copyTo` 默认 8192；源站 JSON 50–500 KB → read 系统调用压到 1/4）
- `MAX_PRESIZE = 4L * 1024 * 1024` + 按 `contentLengthLong` 预分配 `ByteArrayOutputStream`
  （原默认 32 字节起步倍增扩容，等于把同一份数据复制数遍；超 4 MB 退回默认策略防坏头撑爆内存）

**教训**：判据必须是"服务端 accept 次数"，不能是"客户端源端口去重"——
Windows 回环会复用临时端口，3 条连接被算成 1 条，对照用例直接失效。

### 8.2 首页首屏：11.7s → 2.4s

`index-load cat=电影 elapsed=11747 firstBatch=11746`（首批与最终**只差 1ms**）
说明「首批即上屏」在电影分类上**从未生效**。两个独立缺陷叠加：

**缺陷一（真正的大头）：`coroutineScope { launch { ... } }` 是同步屏障**

```kotlin
// 修复前 —— 注释写"后台补齐"，实际是前置串行步骤
coroutineScope { launch { runCatching { resolveTypeIds(sources, categoryName, 999) } } }
```

`coroutineScope` **等所有子协程结束**才返回，于是"先把全部 tier、全部源的分类表
解析完，才去拉列表"。改用仓库自有作用域：

```kotlin
private val bgScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)
// ...
bgScope.launch { runCatching { resolveTypeIds(sources, categoryName, 999) } }
```

用 `SupervisorJob` 而非普通 `Job`：补齐失败不该连坐整个仓库。

**缺陷二：`awaitAll()` 是整批屏障**

原实现「取一批 → `awaitAll()` 等整批 → 判首批」。批里只要有一个慢源，
整批都被它拖住，首批判据也就跟着推迟——门槛早就够了，但没人去判。

改为滑动窗口（判据在 `domain/page/ListBatch.kt`，纯函数可穷举测试）：

```kotlin
fun windowFor(firstEmitted: Boolean, gateLimit: Int, remaining: Int): Int {
    if (remaining <= 0) return 0
    val want = concurrencyFor(firstEmitted, gateLimit)
    return if (want < remaining) want else remaining
}
```

一个结果回来就补一个任务，每个结果落地立刻判一次首批门槛。慢源只拖住它自己。
`remaining` 上限必须有——否则会空转等一个永远不会来的位置。

真机实测（`pm clear` 后冷启动，同一设备同一网络）：

| 分类 | 修复前 firstBatch | 修复后 firstBatch | 修复后 elapsed |
|---|---|---|---|
| 电影（冷启动） | 11746 | **2435** | 3037 |
| 电视剧 | ≈elapsed | 1248 | 1946 |
| 综艺 | — | 1413 | 1793 |
| 动漫 | — | 1320 | 2145 |

电影分类用户提前约 **9.3 秒**看到内容。

### 8.3 跨源候选：14–22s → 4.8–6.6s

`findAltSources` 用 `tasks.awaitAll()` 等**全部**源跑完。探针：
`alt-sources-loaded elapsed=14824 / 14961 / 14310 / 21741 / 19363`，而候选数只有
n=4~15 —— 早在第一两轮就已够用，后面十几秒全在等慢源。

加预算（`domain/page/PageBudget.kt`）：

```kotlin
const val ALT_SOURCES_BUDGET_MS = 6_000L
```

超时后 `out` 里已收集到的候选照常返回：这条路径是"多给几个换线选项"，
少几个候选远好过让用户对着转圈等 20 秒。

修复后实测：`elapsed=6613`、`elapsed=4820`。

### 8.4 内嵌位换源：按列表顺序等 ≠ 先完成先返回

`resolveInlineByAltSource` 注释写"逐个 await：先完成的先返回"，但代码是
`for (d in deferred) d.await()` —— **按列表顺序**等。第 1 个候选若最慢，
第 3 个早就成功了也照样要等第 1 个失败才轮到它。改用 `select` 等最早完成的那个。

`pre-resolve` 实测：修复前 11440 / 12145 / 11407 / 16207 / 33911 ms
→ 修复后 2454 / 3526 / 3046 / 5195 / 3030 ms。

### 8.7 第三波：层间流水线 + 映射命中即拉列表（2026-10-24 深夜）

**回退现象**：§8.6 的 warmup 回退 3 后，真机 firstBatch 从 4840（warmup=1
形态）涨到 6881→8402——用户体感「优化回去了」。Context7 查证 OkHttp
连接池/HTTP-2 结论：SEC-001 禁第三方库，且 `f1d7861` 已实测 HttpURLConnection
keep-alive 复用无问题，**瓶颈在编排不在 HTTP 栈**。

**根因（两个）**：

1. `resolveTypeIds` **层间串行**：tier1 的 hhzy 1.4s 命中后，必须等
   jyzy/huyazy 跑满 3s 超时才进 tier2（tier2 又要 1-2s）——warmup=3 的
   全部代价都落在首屏关键路径上。
2. `select` 返回 null 的**语义混淆**：源失败（resolveOne 返回 null）与
   预算超时（withTimeoutOrNull 返回 null）被同一处 `if (r == null) break`
   处理——源失败会误触收口、连锁取消同层其他在飞源。

**改动**（`SourceRepository`）：

| 改动 | 说明 |
|---|---|
| `resolveTypeIds` 层间流水线 | 某层首个命中即放行下一层（每轮最多一层，空手不越层），统一 select 收集 |
| null 语义分离 | select 改 `select<Boolean>`：源完成在回调里收集（null 仅表示未命中），整体 null 才是预算到点 |
| `fetchByCategory` 映射即拉 | 映射命中即投递任务队列（`onMapped` 回调），首个映射到位立即拉列表；`fetchFromMapped` 删除，列表消费与映射生产并成一个循环 |
| 后台补齐延迟 3s | warmup=999 补齐在 t=0 启动会把全部 tier 分类表请求塞满全局闸门、饿死首屏列表请求（实测 26s 零结果且无失败日志——请求根本没发出） |
| 无进展硬底 10s | resolver 在「一条映射都没有」时原不受预算约束，全挂时 join 死等 26s 击穿页面预算；现在 no-progress 10s 硬底保证错误页在 15s 内出现 |
| 停用死源 dbzy | PC 侧代理/直连 https 均 502（源站网关死亡），真机 DY/Net 多次 UnknownHost/超时；每次冷启动白吃 8s 超时 |

**实测（真机，蜂窝 + Clash 环境）**：

- 冷启动（`pm clear`）：`firstBatch=2090 elapsed=3477 n=41`——对照串行版
  6881→8402、warmup=1 形态 4840、最初 12263。**历史最快，且多源混流**。
- 热切分类（首次进入，探针双值 ms）：电视剧 1336/2103（n=60）、
  综艺 1997/2127（n=39）、动漫首批 3086。
- 翻页：`page=2/3/4 elapsed=2186/2062/2231 n=40 pageCount=267`。
- 海报全部正常（`docs/screens/r7/06-pipeline-cold.png`、`07-hot-anime.png`），
  多源混流下无单源依赖。

**验证**：单测 / `assembleDebug` 全绿。

**未验证**：弱网（丢包/高延迟）下的流水线行为；`TYPE_RESOLVE_BUDGET_MS`
在更快网络下的收紧空间。
