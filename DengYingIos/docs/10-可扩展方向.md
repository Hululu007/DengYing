## 2. 可接入的内容维度

每一项给出四件事：**接入方式**（复用哪层抽象）、**实现成本**、**维护成本**、**风险与前置条件**。
成本单位是「一个人一次专注的批次」，按本轮实测的批次耗时标定：

- **S** = 半天内，通常一个提交
- **M** = 1~2 天，一个批次 + 一组金样本
- **L** = 3~5 天，需要独立设计小节
- **XL** = 一周以上，且**可能白干**（逆向类）

### 2.1 更多 CMS 标准源（最低成本，推荐先做）

**接入方式**：`CmsParser` 已经把苹果 CMS v10 的 `ac=list` / `ac=detail` / `ac=videolist`
全形态吃透了（174 行），`CmsAdapter` 只做 HTTP 控制流（108 行）。**加一个源 = 在
`shared/src/commonMain/kotlin/com/dengying/player/core/Sources.kt` 的 `CmsSources.list`
里加 6 行**，不需要写任何新代码。

**实现成本**：**S**。前提是找到可用的 CMS 采集站（国内这类站点有几十个，`?ac=list` 一测即知）。

**维护成本**：**L**。这类站点的生命周期通常以月计，但死亡是「硬死」——`ac=list` 直接
超时或 502，用户侧表现为该源变红，不会静默出错。按 §4.4 的三关法复检即可。

**风险与前置条件**：

1. **必须过播放关才开**（`docs/04` §15.7.4 的 R-4）。本轮 12 个源的 `ac=list` 全部恢复
   200 且总量过万，但当年停用理由是「分片不可达」——列表活着完全不代表能播，这是本轮
   最贵的教训。
2. **`tier` 字段决定搜索并发顺序**，新源按实测速度排，不要一律塞 `tier = 3`（那会让它
   排在所有源之后，用户体感为「这个源没结果」）。
3. 同名源去重：`sdzy` / `sdzy2` 是同 api 的重复条目，加源前先查 `api` 是否已存在。

### 2.2 更多网站型（正则/XPath）源（成本中等，衰减最快）

**接入方式**：`WebParser`（389 行）已支持三种详情形态——**容器型**（`seasonListPattern`
切段 + `reverseEpisodes` 逆转选集）、**锚点面板型**（`id="downN"` 切段）、**全页型**；
搜索/详情/播放三层各有独立入口。加一个源 = 在 `Sources.kt` 写一条 `WebRule` 声明
（`WebSearchRule` + `WebItemRule` + `WebLineRule` + `WebEpisodeRule` + 可选 `WebPlayRule`）
+ 一组 `WebGoldenTest`。

**实现成本**：**M**。规则是声明式的，但**每个字段都要对着真实 HTML 试错**——本轮 15.3
农民影视与 15.4 两个BT 都出现过「规则写完后正则 0 命中，改用锚点/容器才通」。

**维护成本**：**H，所有维度里最高**。网站改版即失效，且失效形态隐蔽：

- `ah_qiyou` 奇优：搜索、详情全通，但播放页 iframe 从「返回 `const Url/Sign/From`」
  改成「直出 139,700 字节 MP4」，换链规则整体过期。
- `ah_nongmin` 农民影视：根路径 200，但正文是「404，您请求的文件不存在」。

两者都是「HTTP 200 + 结构变了」，靠状态码完全看不出来，只能靠内容判据（见 §3.1）。

**风险与前置条件**：

1. **必须有 playGap 兜底**。半死形态（能搜不能播）比全死更伤——用户搜到条目、点进去
   播不了，体验比搜不到更差。`ah_qiyou` 的做法是保留 `enabled = true` 并写 `playGap`，
    由 `DetailScreen.kt:454` 的 `InlineNotice` 显式告知。
2. **HTML 实体不解码是既有契约**。`WebParser.absolutize` 不做 `&amp;` 解码，因此
   图片 URL 里带 `&amp;` 会原样传给下游。新增源若依赖实体解码，需要先改 `absolutize`
   并补金样本——那是一次数据契约变更，不是加源。
3. **`sniffMedia` 的 `sniff` 参数不参与筛选**（历史既有行为，已在 Kdoc 注明不要顺手修）。
   新源若依赖白名单过滤，要先修这个方法。

### 2.3 需签名/wasm 的源（成本最高，方法论可复用）

**接入方式**：先走「前端也是线索源」这条路（§3.5），把签名算法逆向成 **commonMain 纯
Kotlin 函数**（不依赖运行 wasm / JS），再配 oracle 金样本。本轮两个BT 的落地形态是
`BttwoSign.kt`（138 行）：`k = Base64(userlink XOR "nbmovie2024secretkey")`、
`s = HMAC-SHA256(key = v, msg = "$p:$t:$v").hex[0:32]`。

**实现成本**：**XL，且可能白干**。15.4 这一批的真实耗时分布是：

| 阶段 | 手段 | 结果 |
|---|---|---|
| 定 `k` | 前端 JS 里读到常量 + XMLHttpRequest 抓包 | 一次命中（base64(XOR)） |
| 猜 `s` | 字符串拼接/HMAC/JSON 模板穷举 **56 万组** | **全部失败** |
| 破 `s` | 反汇编 wasm 到 WAT（18,639 行）→ 定位 `f17` = SHA-256 核心 | 定位到算法族 |
| 定稿 `s` | **给 wasm 插桩 trace**，打印每次 SHA-256 输入块 | 一次命中 HMAC 结构 |

即：**穷举 56 万组没成功，一次插桩就破了**。这个对比决定了方法论（§3.3）。

**维护成本**：**M**。算法一旦变更（改 key、改消息模板、换 wasm），金样本会立刻红——
这是好事，比静默失败强。

**风险与前置条件**：

1. **必须有 oracle 才能守住**。没有 oracle 就只能靠「端点返回 200」这一条判据，
   而端点返回 200 不代表返回的是这个视频的地址。两个BT 的守卫是 48 组
   wasm 输出快照（`golden/bttwo_sign.txt`）+ 真实端点 200 两条并列。
2. **签名算法的输入必须能从前端拿到**。两个BT 的 `userlink` 匿名也下发（藏在详情页
   `x-data` 里），这是全链能闭环的前提。若某源的密钥只在 App 二进制里、需要登录才下发，
   客户端复刻就是不成立的——先验证「匿名能不能拿到全部输入」再动手。
3. **`nbmovie.wat` / wasm 本体不入库**（`.gitignore` 管理），只留输出快照。原因：体积大
   且属第三方产物。

### 2.4 发现类扩展（守红线，成本可控）

**接入方式**：`DiscoverFeed` / `DiscoverItem` / `DiscoverParser` / `DiscoverAdapter` 四件套
已独立成型。加一个榜单 = 加一个 `DiscoverKind` 枚举值 + 一个 `parseXxx` 函数 +
一个 URL 构造函数 + 一组测试。**不要**把它塞进 `CmsSource` / `FetchResult` 体系——
理由写在 `docs/04` §15.6.1（站外元数据不是播放源、联想词不是作品、风控属第三类失败）。

**实现成本**：**S~M**，取决于端点是否公开、是否需要签名。

**维护成本**：**M**。公开端点会变、会有风控、会改字段。

**风险与前置条件**（15.6 已定的三条红线，任何扩展都必须守）：

1. **不做个性化推荐**：不带用户标识、不存偏好、不按点击重排。
2. **不引入账号**：不使用 Cookie 持久化到 `KeyValueStore`，单次会话即弃。
3. **不上报**：不实现任何埋点/ulog。

具体到已知候选：

| 候选 | 现状 | 判断 |
|---|---|---|
| 爱奇艺搜索联想 `suggest.video.iqiyi.com` | ✅ 已接（`DiscoverKind.IqiyiSuggest`） | 可继续扩：同一域的 `?if=mobile&key=` 还有 `attributes`/`show_query_count` 可用 |
| 爱奇艺其它公开端点 | 未验证 | 需先探活；若要求 `Referer` 之外的身份凭据即放弃 |
| 豆瓣 `movie.douban.com/j/new_search_subjects` | ⚠️ 一次性可用（20 条），随后 IP 级风控 | **不宜作为主入口**。本机 IP 已被临时拉黑，`{"msg":"检测到有异常请求从您的IP发出"}` |
| 豆瓣 frodo | ❌ key 已死 + 需 `_sig` 签名 | 见 §4.2，不做 |
| 其它平台公开榜单（B 站/优酷/TMDB 等） | 未验证 | 值得试。B 站公开榜单无需登录即可读，是最省事的候选 |

### 2.5 播放链增强（清晰度 / HLS 变体）

**接入方式**：`domain/playback/HlsVariants.kt`（215 行）已有 master m3u8 解析能力，
`PlayerEngine` 契约已抽出（`setMedia(url, headersJson, startPositionMs)` / `play` / `pause` /
`seekTo` / `setSpeed` / `release` + `PlayerListener`）。加清晰度切换有两条路：

| 路径 | 做法 | 成本 | 说明 |
|---|---|---|---|
| A. 换链前选码率 | 在 `resolvePlay` 之前挑 master m3u8 里的某个 variant | **S** | 改动在解析层，不动播放引擎；本轮两个BT 的 `quality_urls` 已天然支持（`q=1080`/`1`/空 三种都回 200） |
| B. 播放中切码率 | `PlayerEngine` 加 `setQuality(bitrate)`，Media3 侧用 `TrackSelectionParameters` | **M** | 要动 `PlayerEngine` 契约 + 三个平台 actual + 真机回归 |

**维护成本**：**L**。这是本地逻辑，与站点无关。

**风险与前置条件**：

1. **HLS 变体标签的格式化已在 P4 解决**：`HlsVariants.kt` 原先用
   `String.format("%.1fM", mbps)`（JVM 专属），P4 已改成整数十分位手工拼装
   （`round(bw / 100_000.0)` → `"${tenths / 10}.${tenths % 10}M"`），取值与旧实现
   逐字节一致。同类风险在新增代码里仍要注意：`commonMain` 用 JVM 专属 API 在
   Windows 上编译**不会报错**（见 §2.6 第 3 条）。
2. **清晰度是「源给什么就是什么」**。`ah_qiyou` 这类网站型源只有一个 m3u8，做码率切换
   没有意义；`ah_bttwo` 的 `quality_urls` 只有一档（1080p）。因此路径 B 的实际受益面
   要先统计「有多少源返回多 variant 的 master m3u8」。
3. Media3 **所有 API 必须主线程调用**（真机踩过 `IllegalStateException: Player is accessed
   on the wrong thread`），路径 B 的 `setQuality` 实现必须记住这条。

## 3. 方法论沉淀

以下七条都是本轮**实测换来**的判断，不是通用建议。写在这里是为了让后来的人少走一遍。

### 3.1 活性判据看内容，不看状态码

本轮遇到的「HTTP 200 但实际不可用」至少有五种形态：

| 形态 | 实例 | 判据 |
|---|---|---|
| 空脚本 | `/static/player/NBY.js`、`BBA.js` 均 `200 + Content-Length: 0` | 看 `Content-Length` 与正文长度，不看 status |
| 业务错误码 | 两个BT 换链 `{"code":404,"message":"record not found"}`（HTTP 200） | 解析 body 里的 `code` |
| 登录墙 | 米米4k `POST /api/parse` → `code:40110`「请登录后观看」 | body 里的 message |
| 路由撤销 | 瓜皮 `{"code":-1,"message":"不存在的路由"}` | body 里的 message |
| 空壳内容池 | 米米4k 曾「`code:0` 但任何关键词 `total:0`」 | 看 `total` 与 `items.size`，不看 `code` |

**结论**：任何探活脚本都必须打「内容判据」（总量、条目数、首条关键字段），只打
状态码的探活一律不可信。

### 3.2 金样本先行

先录真实响应入库，再写解析代码。好处有三：

1. 解析器的期望值来自实测输出，而不是脑补（本轮多次出现「我写错了期望、实现是对的」，
   如 `Tv189Parser.episodeNo` 全部返回 0 是上游缺陷、`trailingNumber(".../999?x=1")` = 1）。
2. 站点改版后金样本会红，第一时间发现。
3. 站点死了以后，金样本是唯一能证明「这段代码当年确实通过」的证据。

**反例**：非确定性端点不能做金样本。`api2233` 的 `nby.php` 同一 token 连续 8 次请求，
响应长度在 `{492, 512, 64}` 之间随机跳变，录制样本 12 次重放 0 次复现 ⇒ 只能录
`placeholder` 那一档，并在文档里如实写明限制。

### 3.3 逆向优先插桩，不要穷举

本轮最贵的一次弯路：为了破 `s = HMAC-SHA256(key=v, msg="$p:$t:$v")`，先做了
**56 万组字符串/HMAC/JSON 模板穷举，全部失败**；随后给 wasm 的 SHA-256 核心函数插桩，
把每次的输入块 dump 出来，**一次命中**（ipad/opad 块直接暴露了 HMAC 结构）。

可复用的插桩手法：

1. 用 `wabt` 把 wasm 反汇编成 WAT（`readWasm` + `generateNames` + `toText`）。
2. 在目标函数入口插入写内存的指令（计数/块数/块内容），把 memory 页数调大留缓冲区。
3. **不用站点 JS 胶水层**，用 stub imports 自己 `WebAssembly.instantiate`——胶水层往往不导出
   memory，看不到内存就没法 dump。
4. 用 `__wbg_now` 之类的桩把时间钉死，才能做差分（`s` 对 `t` 敏感，1ms 变化即不同）。

**判据**：如果穷举 1 万组没命中，就停手转插桩。算法的输入一定在内存里，不在字符串空间。

### 3.4 探活不能推翻播放侧结论

一批 tier3 源的 `ac=list` 本轮全部恢复 200 且总量过万，但它们当年停用理由是「分片不可达」。
列表活着 ≠ 能播。这条写成 `docs/04` §15.7.1 的 R-4 原则，并用三关法（列表/详情/播放）
落地成可复检的流程。

### 3.5 前端也是线索源

需要签名的源，答案往往在站点的公开前端里，不需要逆向 APK：

1. `playerconfig.js` 告诉你播放器类型与是否走第三方解析（`ps:"0"` vs `ps:"1"`）。
2. `player.js` 里的 `document.write('<script src="'+Path+PlayFrom+'.js">')` 告诉你
   解密器路径规律（`/static/player/{PlayFrom}.js`）。
3. 播放页内联的 `var player_aaaa={...}` 直接给出 `url` / `url_next` / `from` / `encrypt`。
4. 详情页的 `x-data="{...userlink:'...'}"` 直接给出签名输入。

**注意**：前端线索拿到后要验证「匿名能否复现」。两个BT 的 `userlink` 每次都变，所以
必须从当前页现取、不能写进金样本做固定期望。

### 3.6 空文件也是证据

`NBY.js` / `BBA.js` 是 200 + 0 字节，同目录 `dplayer.js`(297B) / `iva.js`(1859B) 正常。
这个对比足以证明**站点自己也没在客户端解密**，比「猜不出密钥」有力得多。判断
「某个功能是不是客户端能做的」时，先看站点自己有没有做。

### 3.7 双实现 parity 是迁移期最可靠的护栏

P3 用「旧 org.json 实现 vs 新 kotlinx 实现逐字段比对」抓出了唯一一处真实语义漂移
（`JsonX.textOf` 对 `JsonNull` 返回 `"null"` vs org.json `optString` 返回 `""`）。
这个手法只在双实现并存时可用，**迁移窗口关闭后就没了**——所以迁移期的 parity 一定要做足。

## 4. 明确不做的

写下来是为了防止后人重挖。每条都附「为什么」与「什么条件下可以重新评估」。

### 4.1 嗅探型解析（无 WebView 架构）

**不做**：不引入 `WebView` 去做「加载页面 → 拦截媒体请求」的嗅探型解析。
**为什么**：`:ui` 是 Compose Multiplatform，`WebView` 是 Android 专属控件，引入它等于
把整条链路焊死在单平台，与 `docs/09` 的多平台目标直接冲突。
**重新评估条件**：若某天确定放弃 iOS/鸿蒙，此条作废。

### 4.2 豆瓣 frodo

**不做**：不使用 `frodo.douban.com/api/v2/*`。
**为什么**：两个 API key 两种 UA 四种 path 共 16 组合全部失败——`0dad551e` 这个 key
直接 `403 invalid_apikey`（已死），换 frodo 正确 UA 则 `400 invalid_request_997`
（`localized_message: "签名缺失"`）。签名为客户端私有算法，无公开资料。而豆瓣的
`new_search_subjects` 又有 IP 级风控（一次性可用，随后 `{"msg":"检测到有异常请求"}`）。
**重新评估条件**：有合法授权的 key，或豆瓣开放公开 API。

### 4.3 NBY / BBA 二层密文

**不做**：不尝试解开 `api2233` 的 `NBY-XMYAES<hex>|<hex>` 二层密文。
**为什么**：站点自己的解密器 `/static/player/NBY.js` 与 `BBA.js` 都是 **0 字节空文件**
（同目录其它播放器脚本正常），说明解密在服务端或根本没在客户端做；`api/nby.php` 又是
非确定性端点（同输入输出随机），`api/bba.php` 返回与入参无关的固定占位密文。
所有密钥候选（placeholder 切段、md5/sha256、tail）配 ECB/CBC 全试过，printable 比例
最高 0.39。
**已交付的替代**：`Ap2233PlayPageParser`（254 行）把播放页层解析做到位，等密文可用时
接上即可；面向用户的文案是「换一条线路或换源播放」。

### 4.4 绕过反爬 / 风控 / 登录墙

**不做**：不做 TLS 指纹伪装、不接代理池、不绕 IP 级限速、不伪造登录态。
**为什么**：ADR-0006 的边界；且这类手段的维护成本是无底洞（对方一改就全废）。
**已记录的同族实例**：素白白 `_0x` 混淆反爬挑战页、豆瓣 IP 风控、米米4k 登录墙——
三者都如实记录为「不可用」，未做绕过。

### 4.5 个性化推荐 / 账号 / 上报

**不做**：发现层不做个性化、不引入账号体系、不上报任何埋点。
**为什么**：15.6 定稿的三条红线（`docs/04` §15.6.1），用户明确定位为「纯聚合入口」。
这三条是产品边界，不是技术限制。

## 5. 优先级建议

按「投入产出比 × 风险」排序，**不是排期**：

| 序 | 方向 | 成本 | 收益 | 风险 | 建议 |
|---|---|---|---|---|---|
| 1 | 更多 CMS 标准源（§2.1） | S | 高（直接扩内容池） | 低（三关法可验） | **先做**，一次加 2~3 个并逐个验播放关 |
| 2 | 播放链增强路径 A（§2.5） | S | 中 | 低 | 顺手做，改解析层不动引擎 |
| 3 | 发现类扩 B 站/优酷公开榜单（§2.4） | S~M | 中（提升「随便看看」体感） | 中（端点会变） | 值得试，守住三红线 |
| 4 | 更多网站型源（§2.2） | M | 高（内容独有） | **高（改版即坏）** | 谨慎，每个源必须配 playGap 兜底 |
| 5 | 播放链增强路径 B（§2.5） | M | 中 | 中（要动引擎契约 + 真机回归） | 等路径 A 落地、统计出多 variant 源占比后再定 |
| 6 | 需签名/需要 wasm 的源（§2.3） | XL | 中高 | **极高（可能白干）** | 只在「匿名能拿到全部签名输入」时才投入 |
| 7 | P5 iOS（§2.6） | XL | 高 | 高（需 macOS） | 见 `docs/09`，等 D-2 决策 |

**一句话总结**：内容维度里**最便宜的扩张是 CMS 标准源，最贵的是逆向签名源，衰减最快的是
网站型源**。三者都要过同一道关——「播放关」，也就是真机或本机直连拿到 `#EXTM3U` 或
`ftyp` 字节流。**没过播放关的源一律不开 `enabled`。**
