## 1. 目标与范围

本计划只优化「点下载到文件落盘」这一段，并把“播放优先”限定为当前代码真正能证明的 API 出网闸门，不再承诺降低 ExoPlayer 的媒体流缓冲。

用户能感知的结果：

1. 同一集 HLS 的分片并行下载，不再一个接一个。
2. 下载行始终显示真实已下载字节；总字节已知时百分比按字节，未知时百分比按分片进度，不再把估算值说成精确百分比。
3. 下载请求走 `HttpClient` 的后台槽位，不占详情、搜索、换链等 API 请求的前台保留位。
4. Android/JVM 的整文件下载边下边写；iOS/OHOS 保留整段下载兜底，不在本计划改行为。
5. 失败时不出现“下到一半、列表却显示已完成”的条目，临时文件会被清理。

不在范围：

- 断点续传、Range 请求、进程被杀后从中断处接着下。`DownloadCenter.kt:29` 已写明不做断点续传，本次保持。
- 下载优先级页面、限速设置页、多集下载的排序/优先级。
- 换网络栈、引入第三方下载 SDK、新建第二条出网通道。所有请求仍走 `HttpClient`。
- 放宽 URL 校验、重定向策略或明文 HTTP 例外。
- 改播放链解析、源启用策略、HLS 变体选择规则。
- 改三端版本号。本计划不发布 Release。
- 修改 `DengYingIos` / `DengYingOhos` 的共享源码副本；本期只保证 `DengYing` 的 Android/JVM 行为。

### 1.1 实施前必须确认的决策

| 编号 | 决策 | 本计划选择 | 不选的原因 |
|---|---|---|---|
| D1 | 流式落盘覆盖哪些平台 | 先做 `DengYing` 的 Android/JVM；iOS/OHOS 继续整段下载 | 当前 iOS/OHOS 传输层都是整段响应，强行切换会让现有整文件下载失败 |
| D2 | 进度文案如何表达 | `bytes` 是主指标；总字节已知才显示字节百分比，未知时显示已下载字节 + 分片进度 | 开始下载前无法稳定知道 HLS 总字节，不能让百分比倒退或提前到 100% |
| D3 | “播放优先”指什么 | 只保证下载不占 API 前台槽位；ExoPlayer 媒体流另列验证 | 播放器用 `DefaultHttpDataSource`，不经过 `HttpClient` / `ConcurrencyGate` |
| D4 | 多集同时下载 | 增加全局单任务队列，`MAX_ACTIVE_JOBS = 1`；其余任务保持 `QUEUED` | 当前 `enqueue` 会让多个任务同时启动，各自 3 路会叠加 |
| D5 | 流式不可用时怎么办 | 回退到 `getBinary + writeBytes`，不能把“没有流式实现”当成下载失败 | 避免 iOS/OHOS 或其他 target 因缺少 `actual` 直接功能回退 |

## 2. 现状事实（来自当前代码，非本次实测）

1. **HLS 分片严格串行。** `DownloadCenter.downloadHls()`（`shared/src/commonMain/kotlin/com/dengying/player/data/download/DownloadCenter.kt:256-298`）对 `plan.resources` 用 `for` 循环，一个分片的 `HttpClient.getBinary` 返回后才发下一个。一集几百个分片时，总耗时约等于分片数乘单片往返。
2. **进度按个数，不按字节。** 同一函数 `:290`：`progress = doneCount / resources.size * 0.95`。前面的小分片和后面的大分片在进度条上等价；`DownloadsScreen` 同时显示的 `bytes` 只是累计值。
3. **整文件先全部进内存。** `downloadFile()`（`:234-254`）一次 `getBinary`，整段 `bytes.bytes` 收齐后才 `DownloadStorage.writeBytes`。JVM 传输层用 `ByteArrayOutputStream` 收满再 `toByteArray()`（`shared/src/jvmSharedMain/kotlin/com/dengying/player/data/net/HttpTransport.jvm.kt:105-110`），一份内容在内存里至少有两份拷贝；`MAX_PRESIZE` 只有 4MB（`:46`）。
4. **下载没有后台档，但播放器也不在这个闸门里。** `HttpClient.send()`（`shared/src/commonMain/kotlin/com/dengying/player/data/net/HttpClient.kt:140-142`）从协程上下文读取 `NetPriority` 并交给 `ConcurrencyGate`；下载路径没有带后台 priority，确实会占前台空位。可是播放器在 `app/src/main/java/com/dengying/player/playback/PlayerFactory.kt:116-143` 直接使用 `DefaultHttpDataSource` / `DefaultDataSource` / `MediaCacheDataSource`，媒体流不经过 `HttpClient`。因此本计划只能证明“API 前台槽位不被下载占用”，不能直接证明“播放不转圈”。
5. **落盘是整块写。** `DownloadStorage.writeBytes`（`shared/src/jvmSharedMain/kotlin/com/dengying/player/data/download/DownloadStorage.jvm.kt:25-34`）收 `ByteArray` 后 `File.writeBytes`；common 契约（`shared/src/commonMain/kotlin/com/dengying/player/data/download/DownloadStorage.kt:9-31`）没有流式写入和读取文件前 256 字节的入口。
6. **失败即整集重来。** `init()`（`DownloadCenter.kt:80-91`）把上次留下的 `RUNNING` / `QUEUED` 改成 `FAILED`，文案「下载中断，请重新下载」。本次不改这个状态口径，只补临时文件清理。
7. **内容校验仍要保留。** `downloadFile` 在落盘前用 `looksLikeHtmlPage`（`:188-196`）挡掉 token 换链失败返回的网页。并行和流式都不能绕过这一步。
8. **下载任务没有全局上限。** `enqueue()`（`DownloadCenter.kt:113`）对每个任务直接 `scope.launch`（`:146`），没有全局队列；用户连续点多集时，多个任务可同时进入 RUNNING。
9. **按字节进度缺少数据通路。** `HttpBinaryResult`（`HttpClient.kt:61-66`）只有 `status`、`bytes`、`elapsedMs`；`getBinary()`（`:184-191`）只返回完整字节，binary 分支（`:155-156`）丢弃了 `RawResponse.headers`，所以当前拿不到每个响应的 `Content-Length`。
10. **`NetPriority` 不能按构造参数创建。** `shared/src/commonMain/kotlin/com/dengying/player/data/net/NetPriority.kt:25-34` 的构造器是 private，只有 `NetPriority.Foreground` / `NetPriority.Background`；必须用 `withContext(NetPriority.Background)` 或 `async(NetPriority.Background)`。
11. **跨端不是同一个 Gradle 构建。** `DengYing/shared` 的 `ohosMain` 不在本构建源集里，iOS/OHOS 的共享源码是各自副本；`DengYingIos` 与 `DengYingOhos` 需要分别编译、分别验证。

## 3. 用户看到的结果

同一集、同一网络下，点下载到「已下载」的时间比现在短。下载行显示真实的已下载字节；总字节已知时才显示精确百分比，未知时显示“已下载 X · 分片 Y/Z”，不再用假百分比制造速度感。

下载进行中，详情、搜索、换链等 API 请求不被下载占满前台槽位。播放器媒体流是否更稳，作为单独的真机观察项记录；没有证据前不写“播放优先已实现”。

失败时仍是现在的提示（「下载失败，请稍后重试」或具体原因），不出现半截文件被标成已完成；整文件流式失败会删除 `.part` 临时文件。

## 4. 改法

按 4.1 → 4.2 → 4.3 的顺序做。先做不改传输契约的 HLS 并行，再做需要流式传输的整文件下载。

### 4.1 HLS 分片并行，但只占后台闸门

在 `downloadHls()` 里把串行 `for` 换成固定 3 路 worker（`Semaphore(3)` 或等价 channel），不把并发数做成用户设置。每个分片请求用 `withContext(NetPriority.Background) { HttpClient.getBinary(...) }` 包住，确保 `HttpClient.send()` 读到后台 priority；不要写成 `NetPriority(background = true)`。

后台档最多 4 个空位，下载用其中 3 个；不修改 `OUTBOUND_LIMIT` 和 `FOREGROUND_RESERVED`。播放列表 `fetchText` 保持前台、串行，不被分片堵住。

分片写入继续使用 `DownloadStorage.writeBytes`，每个分片一个文件，文件名用 `plan` 里的 `localName`，不互相覆盖。单个分片失败时取消同一 `coroutineScope` 的其余 worker、删除任务目录、整集标 `FAILED`；不做“跳过坏分片继续下”，否则本地 m3u8 对不上。

全局任务数增加一个单任务闸门：`DownloadCenter` 内维护 `MAX_ACTIVE_JOBS = 1` 的队列，`enqueue` 先把任务置 `QUEUED`，拿到令牌后才 `launch`。这是为了让“每任务 3 路”不会在多集同时下载时叠加；不新增下载优先级或限速 UI。若产品要求多集并行，另立全局预算方案。

进度分两层：

- `bytes = doneBytes` 始终是真实累计已下载字节。
- 每个分片响应如果拿到 `Content-Length`，把它记入 `knownBytes`；只有能覆盖全部分片时才把 `progress` 设为 `doneBytes / knownBytes`。
- 总字节未知时，`progress` 继续按已完成分片数推进，但 UI 同时显示 `bytes`，文案明确“百分比按分片估算”，不说成按字节。
- 最终完成时 `progress = 1f`；任何百分比都单调不减，且完成前不超过 0.99。

`DownloadCenter.update()`（`:306-313`）现在每次分片都 `persistLocked()`，并行后改为每增加约 256KB 或每 500ms 落一次盘；任务完成、失败、取消时必须强制持久化，不能只靠节流后的最后一次。

`fetchText` 发起的 m3u8 请求仍然只走一次；分片并行不改变本地播放列表的生成顺序。

### 4.2 整文件边下边写

先给 `HttpBinaryResult` 增加可选的 `contentLength: Long?`，从 `RawResponse.headers` 读取，`HttpClient.send()` 的 binary 分支不要再丢掉 headers。这样整文件下载在响应头阶段就能知道总字节，HLS 也能记录每个分片的长度。

在 `HttpTransport` 增加流式 `sendStreaming` 契约：响应头先回调，响应体按块回调，最终返回 `status`、`contentLength`、`bytesWritten`。`HttpClient.streamBinary` 在调用它之前必须走同一 `ConcurrencyGate`、`NetPriority`、连接/读取超时和 URL 校验；`sendStreaming` 自身复用传输层的重定向口径，不能新建第二条出网通道。JVM/Android 提供真实流式 actual；iOS/OHOS 可以返回 `unsupported`，由下载层回退，不得把“不支持流式”当失败。若选择新增 common `expect`，必须给每个 target 补 actual；`DengYingOhos` 的副本不在本构建，单独处理。

`HttpClient` 增加一个仅供下载使用的 `streamBinary` 入口，内部仍走同一 `send` 的请求构造、优先级与闸门；不要在 `DownloadCenter` 里直接 `new HttpURLConnection`。

整文件下载不要直接把 `downloadFile()` 改成“必须流式”。新增内部 `DownloadIo` 门面，至少包含：

- `suspend fun getBinary(url, headers): HttpBinaryResult`
- `suspend fun streamTo(relPath, url, headers, onProgress): StreamResult`
- `fun writeBytes(relPath, bytes): Boolean`

`DownloadCenter` 默认使用现有 `HttpClient + DownloadStorage` 的整段实现；Android/JVM 提供 `streamTo` 的流式实现。流式实现仍走上面同一个 `HttpClient.streamBinary`，不绕过闸门。iOS/OHOS 或任何没有流式实现的 target 让 `streamTo` 返回 `unsupported`，`downloadFile()` 回退到 `getBinary + writeBytes`；不能把“没有流式实现”直接标 `FAILED`。

JVM/Android 的流式实现按块读取响应体，块大小使用 common 常量或实际的 32KB 缓冲；不要把 `HttpTransport.jvm.kt:37` 的 private `IO_BUFFER` 直接引用到 common。写入使用 JVM actual 的 `writeChunks`（或在 JVM 内部实现等价写入），先写 `relPath + ".part"`，成功后再原子 rename 到最终路径；失败、取消、HTML 校验命中时删除 `.part`。

网页冒充视频的校验不能丢：流式收到第一块后保留前 256 字节，立即跑现有 `looksLikeHtmlPage`；命中就中止、删除 `.part`、任务标 `FAILED`，文案仍是「下载到的是网页而不是视频，请换源重试」。不要等整个网页下载完再读文件；`DownloadStorage` 当前也没有读取文件前缀的 API。

整文件下载同样使用 `withContext(NetPriority.Background)`。`contentLength` 已知时，`progress = bytesWritten / contentLength`；未知时只更新 `bytes`，完成时置 1.0，不伪造百分比。进度更新同样按 256KB / 500ms 节流，完成和失败强制落盘。

### 4.3 失败、清理与探针

- 所有流式写入先写 `.part`；成功 rename 后才允许 `DONE`。
- 分片失败删除任务目录；整文件失败删除 `.part`；进程被杀后由 `init()` 清理遗留 `.part`，不把残留文件当成可播放文件。
- `download-done` 探针补 `elapsedMs`；可增加 `download-start` 只记录任务 id，不记录完整播放地址。
- `looksLikeHtmlPage` 的判定字不改；`HlsVariants.pickDefault` 的选流规则不改；URL 校验、重定向策略、明文 HTTP 例外不改。
- `init()` 继续把上次的 `RUNNING` / `QUEUED` 标为 `FAILED`，只额外清理 `.part` 残留。

### 4.4 明确不改的部分

- 不改 `HlsVariants.pickDefault` 的选流规则。下载仍下“当前默认变体”，不自动改下最低码率来换速度。
- 不改 `looksLikeHtmlPage` 的判定字。
- 不增加同时下载的任务数；本计划用 `MAX_ACTIVE_JOBS = 1` 把多集任务排队，不新增调度 UI。
- 不改三端版本号；本计划不发布 Release。

## 5. 验证

### 5.1 单元测试

- `rtk gradlew :shared:jvmTest`：现有 `HlsOfflineTest`、`DownloadContentGuardTest` 必须仍过。
- 新增 `DownloadCenter` 测试，用 fake `DownloadIo` / fake storage，不依赖真实网络：
  - 同一 HLS 任务的在途分片峰值不超过 3。
  - 每个分片请求的协程上下文带 `NetPriority.Background`。
  - 第二个 `enqueue` 在第一个任务结束前保持 `QUEUED`，不启动第二个任务。
  - 一个分片失败时，其余 worker 被取消，任务为 `FAILED`，任务目录没有完整播放列表或可播放半成品。
  - 进度单调不减，完成前不超过 0.99，完成时等于 1.0。
  - `Content-Length` 未知时 `bytes` 仍增长，百分比按分片估算且不倒退。
  - 流式实现不可用时回退到 `getBinary + writeBytes`，任务仍可成功。
  - `writeChunks` / 临时文件路径拒绝 `../` 和绝对路径。
  - 首块像 HTML 时任务失败、`.part` 被删除。
- 如需 Android actual 编译，先确认任务名；当前 `shared/build.gradle.kts:28` 只明确把 `:shared:jvmTest` 写成主单测入口。可执行 `:shared:compileDebugKotlinAndroid`（若任务名不同，以 `gradlew :shared:tasks` 为准），不要凭空使用未确认的 `:shared:testDebugUnitTest`。
- 如改动 `DownloadsScreen` 的文案或字段，补跑 `:ui:compileDebugKotlinAndroid`；如改动共享模型序列化，补跑相关 `:shared:jvmTest` 和 `:app:testDebugUnitTest`。
