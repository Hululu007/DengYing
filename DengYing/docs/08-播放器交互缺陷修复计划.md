## 1. 范围

本计划记录播放器全屏交互反馈和详情页内嵌位退出后的残留问题。实现前需要依据本计划确认设计与验收标准。

| ID | 用户报告 | 代码初查 | 目标行为 |
|---|---|---|---|
| P-01 | seek 时没有缓冲环 | `PlayerScreen` 的 `PlayerView` 设置 `SHOW_BUFFERING_NEVER`；Compose 层另有 `s.buffering` 指示层。需确认用户遇到的是 seek 后未进入缓冲态，还是指示层被画面/手势状态遮住 | seek 后播放器未就绪时持续显示缓冲指示；播放器就绪或报错后正确收起，错误提示优先 |
| P-02 | seek 滑动没有动画或主流交互反馈 | `PlayerScreen` 有拖动目标时间提示；当前用 `detectDragGestures` 判方向并在松手提交。需要对照实际 UI 确认反馈缺口 | 横向拖动时清楚显示目标时间与快进/快退差值；松手后执行一次 seek，并以短暂、平滑的视觉反馈收尾 |
| P-03 | 双击播放画面不能暂停 | 当前全屏 `detectTapGestures` 只处理单击切换控制层，没有双击回调 | 双击画面切换播放/暂停；单击显隐控制层；手势不误触发 seek |
| P-04 | 左侧上下滑不能调亮度 | 当前全屏拖动只识别横向 seek，竖向移动不会执行亮度调整 | 在画面左侧竖向滑动调整当前播放窗口亮度，并显示即时数值反馈 |
| P-05 | 右侧上下滑不能调音量 | 当前全屏拖动只识别横向 seek，竖向移动不会执行音量调整 | 在画面右侧竖向滑动调整系统媒体音量，并显示即时数值反馈 |
| P-06 | 返回详情页后内嵌位仍有残留 | `InlinePlayer` 已有 `hidden` 退出态处理的代码说明；用户报告问题仍存在，说明现有处理未覆盖实际返回路径或时序 | 返回后内嵌播放器、控制层和占位内容均不残留；详情页布局稳定，重新进入详情页时状态正确 |

## 2. 设计约束

1. 全屏手势由 `ui/pages/PlayerScreen.kt` 协调。手势分类与播放/暂停调用由 `PlayerViewModel` 暴露窄接口；平台亮度和系统音量适配放在 `ui/platform/`，不把 Android 窗口或音频 API 放入 `domain` 或 `playback`。
2. 缓冲状态仍以播放引擎事件为准。UI 负责呈现状态，不根据拖动动画自行推断播放器已经缓冲。
3. seek 预览期间只更新目标位置和提示；松手时提交一次 seek。拖动取消时恢复原预览状态。
4. 左右区域手势只在播放画面有效。横向 seek、纵向调节、单击和双击需采用明确的方向阈值与手势优先级，避免一次手势触发多个动作。
5. 亮度调节需定义窗口亮度范围、系统自动亮度下的行为和恢复规则；音量调节需使用媒体音量流并遵守系统音量上下限。具体数值显示格式在实现设计中确定。
   - **定稿**：亮度作用于**当前窗口**（`screenBrightness`，范围 0.01..1），起点取窗口覆写值或系统亮度；**离开播放页恢复系统值**。音量作用于 `STREAM_MUSIC`，按系统档位上下限夹取。反馈格式为「亮度/音量 + 百分比」。
6. 内嵌位退出修复需先追踪导航返回、Compose dispose、共享播放会话和 `hidden` 状态的时序，再决定清理责任归属。不能以固定延时隐藏作为唯一正确性保证。
   - **定稿**：不使用延时。清理责任归**导航状态**：`pageActive = (currentBackStackEntry.id == 本页 entry.id)` 为假即只留黑底。`ON_STOP` 的 `hidden` 保留为应用退到后台时的补充路径。

| ID | 根因（经代码定位） | 修法 | 主要位置 |
|---|---|---|---|
| P-01 | `Media3Engine` 的缓冲上报**开始与结束不同源**：开始由 `STATE_BUFFERING` 触发，结束由 `onIsLoadingChanged(false)` 且 `playbackState == READY` 补发。播放开始时 `onPlaying` 已让 UI 自行清掉缓冲环，但引擎侧的 `lastBuffering` 仍是 `true`；此后 seek 触发的 `STATE_BUFFERING` 被去重条件吞掉 → 无缓冲环 | 缓冲上报收敛到 `reportBuffering(active)` 单一出口，只由 `playbackState` 驱动：`BUFFERING → true`，`READY / ENDED / IDLE → false`。`onIsLoadingChanged` 不再参与缓冲判定 | `playback/PlayerFactory.kt` |
| P-02 | 提示浮层是**突然出现/突然消失**的一行文字，没有方向提示，也没有收尾反馈 | 中心浮层改为「方向图标 + 目标时间 + 差值」，出现放大淡入 120ms、收尾缩小淡出 150ms；方向以「目标 vs 当前」判定，与差值符号同源 | `ui/pages/PlayerScreen.kt` |
| P-03 | 全屏手势只有单击回调，没有双击回调；内嵌位同样只有单击 | `detectTapGestures(onTap, onDoubleTap)`：单击切换控制层，双击切换播放/暂停并闪现动作图标（⏸/▶，600ms）。单击因此延迟约 300ms（区分双击的固有代价，主流播放器一致） | `ui/pages/PlayerScreen.kt`、`ui/components/InlinePlayer.kt` |

## 6.7 第四轮：P-02 二次复现与真实根因（2026-10-18）

用户反馈「直接滑屏幕没有进度条动画」，随后「内嵌滑动没有动画」。§6.5 把 P-02
记为"预览反馈通过"，那是在**控制层可见**的前提下测的；本轮把两个前提补上后
复现到两处独立缺陷。

### 6.7.1 复现证据（vivo V2419A / Android 16 / 1216×2640 无线 ADB）

| 场景 | 操作 | 探针 | 画面 |
|---|---|---|---|
| 全屏 + 控制层**已自动隐藏** | 横向滑动 1400px | `seek-start from=3080823` → `engine-seek target=5388176` → `STATE_BUFFERING` → `seek-commit` | **零反馈**：既无浮层也无进度条 |
| 详情页内嵌位 | 横向滑动 750px | `engine-seek target=3054702` | **零反馈**：内嵌位当时根本没有横滑处理，手势被当成点击 |

两处都证明"seek 生效但屏幕无反馈"——播放链路没问题，问题在呈现层。

### 6.7.2 四个根因

| # | 根因 | 位置 | 修法 |
|---|---|---|---|
| 1 | 预览浮层写在 `ControlOverlay` 内部，被 `if (s.controlsVisible)` 一起挡掉。控制层 4 秒自动隐藏后滑动，浮层永远不出现 | `PlayerScreen.kt` | 浮层提到 `PlayerScreen` 顶层，独立于控制层显隐 |
| 2 | 手势**不唤出**控制层，底部进度条不跟着手指走 | `PlayerViewModel.onSeekStart` | 手势开始即 `controlsVisible = true`；松手后 `scheduleHide()` 重新计时 |
| 3 | 差值基准用 `state.curTime`。`curTime` 每秒被播放进度覆盖，同一次按压停住不动时差值自己缩水、方向可能翻 | `PlayerViewModel` + 浮层 | 起点进 `UiState.seekStartMs`，差值一律以手势起点计算（`SeekPreview.deltaLabel`） |
| 4 | 内嵌位只有 `detectTapGestures`，**没有横滑分支** | `InlinePlayer.kt` | 补 `detectDragGestures`：横滑主导 → 预览，松手提交；竖向 → 作废不误触 |

附带修掉的两个连带缺陷：

- **`pointerInput(Unit)` 捕获旧值**：lambda 里直读 `curTime` / `totalTime` 会永远拿到首次组合值。
  真机探针出现 `engine-seek target=0`（松手直接回片头）。改用 `rememberUpdatedState`。
- **隐藏计时器打断拖动**：`scheduleHide()` 到期时若正在滑动，会在手指按着时关掉控制层。
  现在到时先查 `dragging || seeking`，是则跳过（探针 `hide-skip`）。

### 6.7.3 结构改动

| 新增 / 改动 | 职责 |
|---|---|
| `domain/playback/SeekPreview.kt`（新） | 位移→目标、比例、方向、差值文案、是否采信引擎位置。纯函数，零 Android 依赖，可脱设备断言 |
| `ui/components/SeekPreviewBubble.kt`（新） | 中心浮层：方向图标 + 目标时间 + 差值，120ms 放大淡入 / 160ms 缩小淡出。**全屏与内嵌共用**，两条路径不可能给出不一致读数 |
| `PlayerViewModel.UiState.seekStartMs`（新） | 手势起点进状态，浮层不再从会被覆盖的 `curTime` 推算 |
| `PlayerViewModel.pendingSeekTargetMs`（新） | 已提交未落地的目标。落地前不采信引擎位置，避免进度条"弹回旧位置再跳过去" |

浮层刻意**不**复制底部进度轨：手势已唤出控制层，进度条就在画面上；
再叠一条居中的同信息轨，截图实测两条一起跳，反而更难读。
