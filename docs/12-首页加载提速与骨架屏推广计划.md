## 1. 目标与范围

本次只做计划，分两件事：

- **事项 A：首页加载速度优化。** 目标是缩短首页从进入/下拉刷新到「用户看到第一批可用内容」的时间，并保证加载过程稳定、不跳动、错误可恢复。
- **事项 B：其他页面借鉴首页骨架屏设计。** 目标是把首页首拉骨架屏的视觉语言（真实版式占位、低对比呼吸动画、尺寸对齐）抽成可复用组件，推广到确有必要的高频等待页。

本计划范围内的「首屏可见时间」以可观测事件为准，不以「转圈消失」作为主观判断。当前仓库**没有**首页推荐链路的首屏耗时基线（[`docs/04-验证记录.md`](04-验证记录.md):111 已记「首屏/搜索 P95 无数据」），因此事项 A 第一阶段是量化基线，再按证据决定优化项优先级。

不在范围：换源解析、播放链路、搜索结果语义、账号、在线源市场；不为提速放宽 URL 校验或新增出网通道；不把播放器 API 类型带入页面层。

## 2. 现状事实（来自当前代码与文档，非本次实测）

1. **首页骨架屏已是「真实版式占位」**：`ui/src/commonMain/kotlin/com/dengying/player/ui/pages/HomeFeedView.kt:410-475` 的 `HomeFeedSkeleton` 用 `rememberInfiniteTransition("home-skeleton")` 做 0.28f→0.62f、900ms、`RepeatMode.Reverse` 的透明度呼吸；块色是 `Palette.TextSecondary.copy(alpha = alpha * 0.35f)`；版式是 16:9 Hero + 两行双列卡 + 一条三卡 rail，尺寸与真实内容一致，避免加载完成跳动。`IndexScreen.kt:521-575` 的 `RecommendPage` 只在首次 `loading && sections.isEmpty()` 时展示它。
2. **首页数据来源与冷启链路**：`IndexViewModel.kt:575-635` 的 `loadRecommend` 首选 AH（`homeSource()` 选 `ah_ap2233`，受 caps 开关约束），失败回退 tv189。`AhHomeAdapter.kt` 对电影/电视剧/综艺/动漫四个分类并发取各 14 条，再批量补全详情，由 `HomeFeedComposer.kt` 合成 hot 池与 rail。推荐页当前**没有磁盘缓存**，只有仓库 TTL 和 `sectionsByPath` 内存态；注释明确「版块流是运营位数据，磁盘缓存收益小」。
3. **已有可借鉴的提速模式**：分类聚合页 `IndexViewModel.loadData` 使用 PageCache stale-while-revalidate：`cache.get(cat,1)` 先显示旧数据，后台刷新；`fetchByCategory` 通过 `onFirstBatch` 在首批（≥8 条）到达即上屏。[`docs/04-验证记录.md`](04-验证记录.md) §16.30 记录下拉刷新提速实测：修复前 `elapsed=5560ms`，修复后首批 `n=21 elapsed=1453ms`、整体 `elapsed=2631ms`。详情页也有「有内容先画内容」和基于路由参数的 `SkeletonInfoBlock`（`DetailScreen.kt:344-350、371-417`）。
4. **其他页面加载态**：`SearchScreen.kt:142-164` 用居中 36dp 转圈 + 文案；`FavoritesScreen.kt:73`、`HistoryScreen.kt:83`、`DownloadsScreen.kt:74` 走空态文案；`SourceStatusScreen`、`MineScreen` 无独立 loading 标记。`DetailScreen` 已有自己的信息块骨架。
5. **公共组件现状**：`ui/components/CommonUi.kt:36/65/101` 提供 `LoadingView`、`ErrorView`、`EmptyView`；骨架逻辑目前内联在 `HomeFeedView.kt`，不是共享组件。
6. **架构边界**：`ui → playback → data → core`；ViewModel 构造函数注入依赖；首页逻辑在 `ui` 与 `shared/data`，不得因提速把平台能力或播放器 API 泄漏进页面层。

## 3. 事项 A：首页加载速度优化

### A.0 量化基线（先测再改）

| 步骤 | 内容 | 产物 |
|---|---|---|
| A.0.1 | 在首页加载链路增加一组轻量耗时探针（沿用现有 `[index-...]`/probe 风格，日志不输出搜索词、完整 URL 或历史）：进入首页/切回首页/下拉刷新三个场景，记录总耗时、`fetchHomeTabs`、`fetchHomeSections`、首次可渲染 sections 的到达时刻、回退是否发生、最终有效卡片数 | probe 行 + 真机截图/记录 |
| A.0.2 | 同一台 vivo V2419A、同一网络条件下冷启与热切各跑至少 5 次，记录中位数与最差值；明确「首屏可见」的定义：第一块 Hero/双列卡实际绘制，而非骨架消失 | 基线表写入 `docs/04` |
| A.0.3 | 与分类页 §16.30 数据对比，判断瓶颈在取 tabs、四分类并发取列表、批量详情补全，还是合成/首帧绘制 | 瓶颈排序，决定 A.1 是否实施 |

说明：探针只在 debug 或现有诊断通道输出，不新增第三方 SDK、不改变 Release 行为。

### A.1 缩短冷启/刷新关键路径（按 A.0 结果取舍）

| 编号 | 候选优化 | 触发条件 | 验证口径 |
|---|---|---|---|
| A.1.1 | **首批即上屏**：参考分类页 `onFirstBatch` 思路，让四个分类中先返回的分类先合成并渲染部分 section，而不是等 `awaitAll` 全部完成；定义最小可展示阈值（如至少一个完整 Hero + 一行卡）并避免后续数据引起大幅跳动 | A.0 显示「等最慢分类/详情批量补全」占主要时间 | 首批到达时间下降；真机录屏/截图确认无整屏重排；最终内容与现版一致 |
| A.1.2 | **缓存策略复核**：评估给推荐页增加短 TTL 的磁盘/内存缓存（stale-while-revalidate），或仅缓存 tabs 与分类列表首 batch；必须与「版块流是运营位数据」的原设计理由权衡，缓存时效和手动刷新绕开缓存要写清 | A.0 显示重复冷启仍长时间等待且网络往返占主导 | 热启命中缓存时首屏时间显著下降；下拉刷新仍强制网络；缓存版本失效/损坏可回退 |
| A.1.3 | **并发与超时治理**：复核四分类 `async` 与详情 `batch` 的并发数、慢源超时、AH→tv189 回退条件；避免单个分类拖死整屏，也不要产生额外重试风暴 | A.0 显示个别分类长尾或回退过慢 | 慢源场景有可重复探针；回退只在真实失败/空数据触发 |
| A.1.4 | **减少首屏无效工作**：确认 `fetchHomeTabs` 是否可缓存/并发进 sections 请求，合成阶段避免在 Grid 首帧前做与可见内容无关的大对象操作；所有改动保持模块边界 | A.0 显示 tabs 或合成阶段占比明显 | 单测覆盖合成输出不变；首帧时间下降 |

> A.1 是候选清单，不是承诺全部实施。实施顺序按 A.0 的数据决定；若 A.0 推翻假设，优先修最大瓶颈并更新本计划。

### A.2 稳定性与回归要求

- 骨架屏展示条件必须准确：首次加载用骨架；有部分数据先出数据；刷新保留旧内容 + 局部反馈；空/错误走已有 `ErrorView`/空态，不出现空白页或「假成功」。
- `refreshRecommend` 仍强制网络；缓存仅用于冷启/切回的过渡，刷新反馈沿用 `notice`（「已刷新 · N 个内容」）。
- 任何缓存/首屏行为变更同步更新 `docs/02` FR-630 的证据与 `docs/04` 的实测章节；NFR-010「冷启动 ≤ 3s」当前标注「REVIEW，无耗时基线」，本事项结束后据实更新，不能拿无证据的推测写「达标」。
- 不改变 `PlaybackSession` 单一事实源和换集/续播不变式；首页只负责内容列表与导航入口。

## 4. 事项 B：骨架屏设计推广

### B.1 抽取共享骨架组件（设计先行）

在 `ui/src/commonMain/kotlin/com/dengying/player/ui/components/` 新增轻量骨架原语（文件命名在实施时定，如 `SkeletonUi.kt`），把她首页已验证的视觉规则参数化：

- 统一呼吸动画：0.28f→0.62f、900ms、reverse；同一页面多个骨架共用同一 `rememberInfiniteTransition` key，避免相位错乱。
- 统一色板：块色 `Palette.TextSecondary.copy(alpha = alpha * 0.35f)`，跟随深浅主题；不用新图标库/位图资源。
- 提供基础原语：`SkeletonBlock`（圆角矩形）、`SkeletonListRows`、`SkeletonGrid`、`SkeletonPosterCard` 等，形状与圆角由调用方按真实版式传参。
- `HomeFeedView.kt` 的 `HomeFeedSkeleton` 改为调用共享原语，视觉与现有截图保持一致；原「尺寸与真实内容一致」注释保留并推广为设计原则。
- 组件保持 `commonMain` 可用，不引入 Android/iOS/鸿蒙专属 API；不把 `LoadingView` 直接替换掉，二者语义不同（骨架=版式占位，loading=无版式/操作反馈）。

### B.2 推广范围与顺序

| 阶段 | 页面 | 加载态现状 | 骨架设计原则 | 不做 |
|---|---|---|---|---|
| B.2.1 | `IndexScreen.kt` 聚合分类页 `PageContent`（`cs.loading && cs.items.isEmpty()` → `LoadingView()`，约 :593） | 居中转圈 | 用与真实宫格同列数、同卡片比例/间距的网格骨架；首批数据到达即整块替换 | 不为已有数据的分页加载加整屏骨架 |
| B.2.2 | `SearchScreen.kt`（`s.searching && s.results.isEmpty()`，:142-164） | 转圈 + tip | 用结果行骨架（封面+两行文字），宽度/高度对齐真实搜索结果；清空搜索词、取消搜索时立即退出骨架 | 不推测搜索词占位、不输出搜索词到日志 |
| B.2.3 | `FavoritesScreen`、`HistoryScreen`、`DownloadsScreen` | 空态文案 | 仅当「确实在读本地存储且无旧数据」时显示短列表骨架；有缓存/历史列表先画列表再后台刷新 | 存储读取很快时不必强行加骨架；空态必须保持原样 |
| B.2.4 | `DetailScreen.kt` 的 `SkeletonInfoBlock` | 已有自定义骨架 | 只做视觉对齐共享原语（圆角、呼吸节奏、色板），保留路由参数里的片名/封面真实信息 | 不替换「有内容先画内容」的快速路径，不改动播放会话逻辑 |
| B.2.5 | `SourceStatusScreen`、`MineScreen` | 无独立 loading 标记 | 仅当新增异步加载时才考虑；否则保持现状 | 不为静态页面制造加载态 |

### B.3 验收口径

- 逐页真机截图/录屏：骨架出现时机正确、与真实内容版式对齐、切换时无明显跳动、深浅主题一致。
- 骨架展示不应掩盖错误或空态；首次加载失败必须能看到 `ErrorView` 与重试入口。
- 共享原语不破坏 `HomeFeedView` 现有布局测试（继续用 `HomeFeedLayoutTest` 等纯函数/布局测试）；新增页面骨架不改变数据源和 ViewModel 状态机。
- 页面/组件变更后跑 `:ui:jvmTest`、`:ui:compileDebugKotlinAndroid`，交付前 `:app:assembleDebug`。

## 5. 执行顺序与依赖关系

1. **阶段 0（事项 A.0）**：先埋点、跑基线、确认瓶颈；同时开始 B.1 的共享组件抽取（互不依赖）。
2. **阶段 1**：按 A.0 结果实施 A.1 中最高收益项；B.2.1/B.2.2 落地网格与列表骨架。
3. **阶段 2**：A.2 回归与数据文档化；B.2.3/B.2.4 推广到次要页面并对齐详情页骨架。
4. **阶段 3**：整体验证、需求矩阵/验证记录同步、版本递增。

依赖约束：事项 B 不得改动数据获取时序来「制造」加载态；事项 A 若改变首屏渲染时机，必须同步更新骨架切换条件与 B.2 的页面判断。

## 7. 风险与未决项

- 首页推荐无磁盘缓存是有意设计；是否改成短 TTL 缓存需要 A.0 数据支撑，并写清运营位时效性与隐私/存储成本。
- 首批即上屏可能带来二次排版跳动；必须先定义「最小可展示阈值」和替换策略，并用真机画面确认。
- 骨架动画若不同页面各写一份，会出现相位/色调不一致；B.1 必须先抽原语再推广。
- 统计口径需明确：探针记录的是到达时刻，不等同于用户主观感知；真机截图/录屏作为补充证据。
- 本计划不涉及 iOS/鸿蒙壳的原生验证；若共享组件改动影响其它平台，需要在各自工程按手册补验，不能声称已验证。
